# MkAIHub 第二阶段闭环实施方案

> 文档状态：M2 实施规划基线
> 版本：v0.3
> 更新日期：2026-08-24
> 开发主线：Python 3.13 + FastAPI 后端、Vue 3 + TypeScript 前端
> 前置文档：[MkAIHub 项目规划](./MkAIHub项目规划.md)、[MkAIHub 首版实现方案](./MkAIHub首版实现方案.md)

## 1. 文档目的

本文档用于明确 MkAIHub 从首版模块骨架进入第二阶段业务闭环时需要解决的问题、实施边界、核心关系、研发批次和验收标准。

本阶段不是重新实现竞赛、任务和展品 CRUD，而是在保留现有模块的基础上，把三者从独立的信息页面连接为可以实际使用、可以追踪结果、可以验证权限的业务流程。

本文件是实施规划，不代表其中列出的数据库表、字段和接口已经交付。批次 7 的业务决策确认完成后，才进入迁移和编码。

## 3. 问题定义

### 3.1 任务“完成”不等于成果闭环

当前任务由发布人直接从 `OPEN` 标记为 `COMPLETED` 或 `CLOSED`，系统没有记录：

- 谁参与或领取了任务。
- 参与人提交了什么成果。
- 成果是否被退回修改。
- 发布人依据什么完成验收。
- 最终成果对应哪一条展品。

因此当前“完成”只表示发布人执行了一次状态操作，不能证明任务已经产生、验收并沉淀成果。

### 3.2 展品没有业务来源

展品已经具备完整内容和附件能力，但目前只知道作者，不知道它是否来自任务或竞赛。由此产生以下问题：

- 任务详情不能展示最终成果。
- 竞赛详情不能展示竞赛任务、各任务成果和获奖成果。
- 展品详情不能解释成果背景、验收结果或竞赛成绩。
- 无法统计任务成果沉淀率、竞赛任务完成率和竞赛成果复用情况。

展品应继续作为统一成果载体，任务和竞赛通过关联记录引用展品，不重复保存展品正文和附件。

### 3.3 竞赛目前没有任务和执行过程

当前竞赛只包含标题、简介、规则和起止时间。普通员工只能查看，管理员只能维护基本信息。系统没有：

- 竞赛包含的任务，以及任务的必做/选做、分值、权重和顺序。
- 报名人或参赛状态。
- 参赛人对各竞赛任务的成果提交。
- 任务提交截止和多轮提交规则。
- 评委、评分或评语。
- 结果发布、名次和获奖信息。

因此竞赛当前是时间化公告，不是可执行的竞赛流程。

### 3.4 提交阶段的可见性和权限未定义

现有展品只有草稿、已发布、已归档三种状态：草稿只对作者和管理员可见，已发布展品对所有登录员工可见。任务发布人或竞赛评委无法查看其他员工的草稿。

第二阶段必须先确认：成果提交时是否要求展品已经公开发布，还是允许受限可见的候选成果。这个选择会直接影响展品状态、查询权限、下载权限和评论规则，不能仅靠前端隐藏入口处理。

### 3.5 现有状态和删除规则不足以承载关联数据

- 任务没有进行中、待验收、退回修改等过程状态。
- 竞赛状态只按时间计算，没有草稿、结果待发布、已归档等运营状态。
- 竞赛当前允许物理删除；产生竞赛任务、报名、任务提交或评审记录后，物理删除会破坏追溯关系。
- 任务完成前不检查是否存在被接受的成果。

第二阶段需要重新定义状态机和删除约束，并由后端服务层统一执行。

### 3.6 首版验收记录与第二阶段验收需要分开

首版已经按简化范围完成自动化测试、部署配置和备份恢复，但浏览器自动化不属于最终简化交付。第二阶段引入跨用户、跨角色流程后，不能继续只依赖 API 和组件单元测试，必须为核心闭环增加浏览器级验收。

## 4. 第二阶段目标

### 4.1 任务闭环

```text
发布任务
  -> 员工参与或领取
  -> 创建并提交展品成果
  -> 发布人验收或退回修改
  -> 参与人重新提交
  -> 验收通过
  -> 任务完成、成果沉淀
```

系统必须能够回答：谁参与、提交了哪条展品、经历了哪些处理、谁在什么时间验收、最终采用了哪个成果。

### 4.2 竞赛任务闭环

```text
管理员创建竞赛
  -> 在竞赛中配置必做和选做任务
  -> 发布竞赛
  -> 员工报名
  -> 参与竞赛任务并提交展品成果
  -> 截止后锁定任务提交
  -> 按任务评审和评分
  -> 汇总各任务最终有效得分
  -> 发布竞赛结果与排名
  -> 获奖展品继续在平台沉淀和复用
```

系统必须能够回答：竞赛包含哪些任务、哪些任务必做或选做、谁报名并完成了哪些任务、每项任务提交了哪条展品、各任务得分如何汇总、谁完成评审、结果何时发布、名次和获奖信息是什么。

### 4.3 展品中心关系

展品继续承担正文、附件、评论和公开分享能力。无论普通任务还是竞赛任务，成果都只通过任务提交关联展品，不再建立一套重复的竞赛投稿正文或附件。

同一条展品未来可能被用于多个任务，因此不在 `artifacts` 表增加单值 `task_id` 或 `competition_id`。展品的竞赛来源通过“展品 -> 任务提交 -> 竞赛任务 -> 竞赛”关系得到。

### 4.4 任务的两种归属

- 普通独立任务：`competition_id` 为空，继续完成参与、提交、验收和成果沉淀闭环。
- 竞赛任务：`competition_id` 指向一个竞赛，由竞赛管理员配置，参赛人通过完成任务获得竞赛得分。

一个竞赛可以包含多个任务；一项任务最多属于一个竞赛。首期不复用同一任务到多个竞赛，避免任务时间、分值和结果归属发生冲突。

## 5. 本阶段范围

### 5.1 包含

- 任务参与或领取。
- 任务成果提交、退回修改、重新提交和验收。
- 任务与展品的双向来源展示。
- 普通独立任务与竞赛任务并存。
- 竞赛内任务的必做/选做、排序、最高分和权重配置。
- 竞赛报名和取消报名。
- 参赛人通过竞赛任务提交展品成果，截止后锁定提交。
- 针对竞赛任务成果的评审、评分和评语。
- 各竞赛任务得分汇总、结果发布和排行榜。
- 竞赛、任务与展品的双向来源展示。
- 与闭环直接相关的个人待办、管理入口和状态通知。
- 后端权限、状态机、结构化日志、迁移和自动化测试。
- 前端列表、详情、表单、操作反馈和浏览器验收。

### 5.2 不包含

- C# 版同步实现。
- 团队创建、组队邀请、队长和成员审批。
- 奖金、支付、提现、财务结算和积分商城。
- 自动评测、代码沙箱、排行榜实时大屏。
- AI 自动完成任务、AI 自动评分或 AI 评委。
- 实时聊天、邮件、短信或企业 IM 推送。
- 展品通用版本管理、复杂内容审批流和公开互联网分享。
- PostgreSQL、对象存储、Redis、消息队列和多实例部署。
- Toolkits、Data Lab、MapOS、RAG、Agent 和 MCP。

### 5.3 本阶段最小化原则

- 先支持个人参与和个人参赛，组队后置。
- 复用现有任务提交、展品和文件能力，不创建 `competition_entries` 或另一套“竞赛成果正文/附件”。
- 待办先采用站内列表和数量提示，不建设独立消息中心或外部推送。
- 排名先支持一次正式结果发布，不建设多轮赛制、晋级树或实时榜单。
- 状态和权限必须由后端强制执行，前端只负责表达允许的操作。

## 7. 建议领域关系

以下是用于范围评审的建议模型，不是最终 DDL。

### 7.1 任务归属与竞赛配置 `tasks`

在现有任务模型上增加：

- `competition_id`：可空外键；为空表示普通独立任务，不为空表示竞赛任务。
- `competition_required`：竞赛任务是否必做。
- `competition_sort_order`：在竞赛详情中的显示顺序。
- `competition_max_score`：该任务原始评分上限。
- `competition_weight`：该任务计入竞赛总分的权重。

建议约束：

- 一项任务最多属于一个竞赛，一个竞赛可以包含多个任务。
- 竞赛专用配置只在 `competition_id` 非空时有效，并通过检查约束保证分值、权重为正数。
- 竞赛发布后，已经产生报名或提交时不能随意移除任务或修改计分配置。
- 竞赛任务截止时间为空时继承竞赛结束时间；单独配置时不能晚于竞赛结束时间。
- 首版已有任务迁移后 `competition_id` 统一为空，保持普通独立任务语义。

### 7.2 任务参与 `task_participants`

建议记录：

- `task_id`、`user_id`。
- 参与状态和参与、退出时间。
- 创建和更新时间。

建议约束：同一用户在同一任务只能有一条当前参与关系；任务关闭或完成后不能新增参与人。参与竞赛任务前必须存在有效的竞赛报名记录。

### 7.3 任务提交 `task_submissions`

建议记录：

- `task_id`、`participant_id`、`artifact_id`。
- 提交轮次、提交说明和状态。
- 提交、退回、验收时间。
- 验收人和验收意见。
- 是否为当前最终有效版本。

建议状态：

```text
SUBMITTED（已提交）
  -> REVISION_REQUIRED（需修改） -> SUBMITTED（重新提交）
  -> ACCEPTED（已验收）
  -> REJECTED（未采用）
```

普通独立任务只有在满足已确认的验收规则后才能进入 `COMPLETED`。竞赛任务允许每名参赛人多轮提交，但只保留一条最终有效提交参与评分；历史提交和处理意见不得覆盖。

### 7.4 竞赛报名 `competition_registrations`

建议记录：

- `competition_id`、`user_id`。
- 报名状态和报名、取消时间。

建议约束：同一用户不能重复报名；无有效报名不能参与竞赛任务。开始或提交截止后是否允许取消，由批次 7 明确。

### 7.5 竞赛任务评审 `competition_reviews`

建议记录：

- `task_submission_id`、`reviewer_id`。
- 原始得分、评语和评审时间。
- 是否为正式评审结果。

评分约束：

- 原始得分必须在 `0` 到任务的 `competition_max_score` 之间。
- 单项计分建议使用 `原始得分 / 最高分 * 权重`，竞赛总分为各任务计分之和。
- 必做任务没有最终有效提交时，参赛人不进入正式排名；选做任务没有提交时按 0 分处理。
- 每名参赛人在同一任务中只取最终有效提交的正式评审结果，旧轮次不重复计分。

若首期只有系统管理员评审，可暂不建立评委配置表；如果允许指定多名评委，则增加 `competition_judges`，并在批次 7 明确平均分、缺评和复核规则。

### 7.6 竞赛正式结果 `competition_results`

建议记录：

- `competition_id`、`registration_id`。
- 汇总得分、正式名次、奖项名称。
- 结果发布人和发布时间。

发布结果时从各竞赛任务的最终有效评审记录计算并写入正式结果快照。结果发布后普通列表读取快照，不因后续数据修正自动漂移；纠错必须走管理员专用动作并记录结构化日志。

### 7.7 展品关系

展品不直接保存单一来源字段。详情页通过任务提交查询来源：

- 任务名称、任务状态、验收状态。
- 如果属于竞赛任务，再展示竞赛名称、任务得分、总名次和奖项。

删除或归档展品前必须检查有效提交关系。已验收任务成果和已发布竞赛结果引用的展品不能物理删除；归档后的可见性规则需要由后端统一处理。

## 8. 建议状态机

### 8.1 任务状态

建议从当前状态扩展为：

```text
OPEN（开放）
  -> IN_PROGRESS（进行中）
  -> REVIEWING（待验收）
  -> COMPLETED（已完成）
  -> CLOSED（已关闭）
```

具体规则：

- 普通独立任务在首个有效参与关系建立后可进入 `IN_PROGRESS`。
- 普通独立任务存在待处理成果时进入 `REVIEWING`，或由提交状态派生页面展示。
- 只有普通任务发布人或管理员可以验收、关闭普通任务。
- 普通任务没有已验收成果时禁止完成。
- 竞赛任务不能因为某一名参赛人完成提交而进入 `COMPLETED`；任务可提交状态由父竞赛、任务截止时间和任务启用状态共同决定，个人完成情况保存在任务提交记录中。
- 已完成或已锁定任务不可新增参与或提交；是否允许管理员纠错重开，需要单独确认。

### 8.2 竞赛状态

竞赛需要区分两类状态：

- 时间状态：`UPCOMING/ONGOING/ENDED`，继续按服务器时间计算。
- 运营状态：建议增加 `DRAFT/PUBLISHED/RESULT_PUBLISHED/ARCHIVED`。

时间状态回答“现在处于什么时间段”，运营状态回答“内容是否发布、结果是否公开”。两者不能混为一个字段。

竞赛开始时开放报名和任务提交，竞赛结束时间作为默认提交截止时间。结果发布前完成各竞赛任务评分和汇总，结果发布后锁定正式排名。

产生竞赛任务、报名、任务提交或评审记录后，不再允许物理删除竞赛，只允许关闭、发布结果或归档。

## 9. 权限原则

| 操作 | 普通员工 | 普通任务发布人 | 系统管理员/竞赛评审人 |
|---|---|---|---|
| 参与开放的普通任务 | 可以 | 可以参与他人任务 | 可以 |
| 参与竞赛任务 | 仅已有效报名相应竞赛时可以 | 不适用 | 以参赛人身份时同普通员工 |
| 提交任务成果 | 仅本人参与的任务；竞赛任务还需有效报名 | 参与时同普通员工 | 管理员不代替员工提交 |
| 查看待验收成果 | 按已确认可见性规则 | 可以查看自己发布任务的提交 | 管理员可以治理查看 |
| 退回或验收普通任务成果 | 不可以 | 可以 | 管理员仅处理异常或按确认规则操作 |
| 配置竞赛任务 | 不可以 | 不适用 | 仅系统管理员 |
| 报名竞赛 | 可以 | 不适用 | 可以以员工身份报名 |
| 评审竞赛任务成果 | 不可以 | 不适用 | 系统管理员或指定评委可以 |
| 发布竞赛结果 | 不可以 | 不适用 | 仅系统管理员 |

所有权限由 FastAPI 服务层校验。列表查询、详情、附件下载和评论也必须应用相同可见性规则，不能只在前端隐藏按钮。

## 10. 页面与接口范围

## 12. 验收场景

### 12.1 任务闭环

1. 员工 A 发布任务。
2. 员工 B 和员工 C 参与任务。
3. B、C 分别创建或选择展品并提交。
4. A 退回 B 的成果并填写意见，B 修改后重新提交。
5. A 验收 B 的成果，拒绝或保留 C 的成果。
6. 任务完成，详情展示最终成果和完整处理时间线。
7. 展品详情反向展示来源任务和验收状态。

### 12.2 竞赛闭环

1. 管理员创建竞赛，并配置一个必做任务和一个选做任务的顺序、最高分和权重。
2. 竞赛发布后，员工 B 报名并进入竞赛任务；员工 C 未报名直接提交竞赛任务成果被拒绝。
3. B 针对任务创建或选择展品并提交，多轮修改后只保留最终有效版本参与评分。
4. 截止前 B 可以按规则重新提交，截止后不能修改；竞赛任务不会因某一个参赛人完成而整体完成。
5. 管理员或指定评委分别对任务最终有效成果评分并填写评语。
6. 系统按 `原始得分 / 最高分 * 权重` 汇总；缺少必做任务的参赛人不进入正式排名，未完成选做任务按 0 分处理。
7. 结果发布前普通员工不能查看内部评分，发布后展示冻结的排行榜、名次和奖项。
8. 展品详情通过任务提交反向展示竞赛、任务得分和竞赛结果。

### 12.3 权限和异常

- 非任务参与人不能提交成果。
- 非任务发布人不能验收。
- 未报名竞赛的员工不能参与或提交该竞赛任务。
- 普通员工不能评审或发布竞赛结果。
- 竞赛任务归属、截止时间、重复报名、无效提交轮次和非法状态转换返回统一错误体。
- 已验收成果和已发布竞赛结果引用的展品不能物理删除。
- 归档内容的列表、详情和附件下载遵守统一可见性规则。

## 14. 迁移与兼容原则

- 新迁移使用日期前缀并从 `20260819_0005` 继续递增。
- 不修改已经提交的首版迁移文件。
- 新增非空字段必须提供可解释的默认值或分阶段回填方案。
- 首版已有任务、竞赛和展品不能因升级失效。
- 旧任务默认保持原状态，不伪造参与、提交或验收记录。
- 旧任务的 `competition_id` 默认为空，继续作为普通独立任务。
- 旧竞赛默认保持现有可见性，不伪造竞赛任务、报名、评分或结果。
- 新增关联后重新验证备份、恢复和 SQLite 外键完整性。

## 15. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 同时改三个模块导致范围失控 | 按任务闭环、竞赛闭环、跨模块体验分批实施 |
| 展品可见性规则被提交关系绕过 | 编码前确认公开/受限方案，统一详情和附件权限 |
| 状态字段继续由路由或前端散落修改 | 状态动作集中到 Service，接口只调用服务 |
| 同一展品多处使用后来源字段冲突 | 统一使用任务提交关系，不在展品上保存单一任务或竞赛来源 |
| 竞赛任务被当成普通任务提前完成 | 竞赛任务整体状态跟随父竞赛，个人完成情况只记录在提交中 |
| 竞赛结果发布后排名漂移 | 发布时冻结正式结果，后续修改必须走管理员纠错规则 |
| 有关联数据后物理删除破坏追溯 | 使用限制删除、关闭和归档 |
| C# 同步拖慢 Python 主线 | 第二阶段明确暂缓 C#，稳定后另行评估 |
| 浏览器流程只靠人工记忆 | 批次 11 建立可重复的多账号验收流程 |
